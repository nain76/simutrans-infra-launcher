# 安全性の設計

この文書は、配信サーバーとランチャーが、どの危険をどの仕組みで防いでいるかをまとめたものです。主にサーバー側の仕組みを説明し、それを受けて確かめるランチャー側の仕組みも最後に触れます。

## 守りたいもの

一番守りたいのは、友人のPCです。ランチャーはsimutrans本体という実行ファイルを友人のPCに入れて起動するので、すり替えられた実行ファイルを入れてしまうと、友人のPCで好きなプログラムを動かされてしまいます。次に守りたいのは配信サーバーで、外から中身を書き換えられたり、置いてはいけないファイルを配ったりしないようにします。

想定している危険は次の4つです。

| 危険 | 例 |
|---|---|
| 配信フォルダの書き換え | IISの設定の不備や、ほかの経路から、配信しているファイルを差し替えられる |
| 通信途中のすり替え | 友人とサーバーの間で、ダウンロード中のファイルを差し替えられる |
| 配ってはいけないものの公開 | セーブデータ、パスワードのハッシュ、バッチファイルなどを配ってしまう |
| 偽のサーバーリスト | 管理者になりすました人が、自分のサーバーリストのアドレスを友人に教える |

## 配信サーバーの守り方

### ファイルを配るだけのサイトにする

配信にはWindows標準のWebサーバー機能（IIS）を使い、公開フォルダ（既定は`C:\simutrans-dist`）のファイルをそのまま配るだけのサイトにしています。プログラムを動かす仕組み（ASP.NETやCGIなど）は入れず、使いません。

公開フォルダの直下の`web.config`で、読み出し（GETとHEAD）以外の要求をすべて断る設定にしています（`requestFiltering`の`verbs allowUnlisted="false"`）。そのため、外からファイルを書き込んだり、消したりする要求は通りません。構築ツールは設定を入れたあと、実際に書き込み要求（PUT）を送り、断られることと、ファイルが作られないことを確かめます。

フォルダの中身の一覧表示はオフにしています。ファイル名を知らない人が、公開フォルダに何があるかを一覧で見ることはできません。IISは`web.config`自体を配信しません。

ファイル名に`+`を含むファイル（`m+10r.bdf`など）を配るため、配信フォルダの`web.config`で`allowDoubleEscaping`を有効にしています。この設定で危険が増えるのは、アドレスを解釈してプログラムを動かすサイトです。このサイトはファイルを配るだけなので、危険は増えません。

### 大事なファイルを公開フォルダの外に置く

公開の設定（`publish-settings.json`）は`server-setup`フォルダに、署名の鍵は`%LOCALAPPDATA%\InfraLauncherServer`に置いています。どちらも公開フォルダの外にあるので、IISからは配信されません。

### 名前を推測されにくくする

サーバーリストのファイル名と、paksetの公開フォルダの名前には、ランダムな文字を付けます（例は`list-7k3qf9x2m4.json`、`pak.NSOTRP32-x8f2k9qa`）。フォルダの一覧表示はオフなので、名前を知らない人はファイルを見つけられません。ネットを巡回するプログラムや、ドメインとポートだけを知っている人に、接続先やファイルを見つけられにくくするためです。

これは見つけにくくするだけの仕組みで、アドレスを知っている人は中身を読めます。書き換えや偽のファイルを防ぐのは、次に説明する署名と確認コードです。本体の公開フォルダ（`engine\<版>`）の版の名前には、中身から計算した値が入るので、同じファイルを持っていない人には推測できません。

### 開けるポートを最小限にする

Windowsファイアウォールで開けるのは、配信用のポート（8080、HTTPSなら8443）、証明書の確認用の80番、simutransサーバーのポートだけです。

### 配るファイルを許可リストで決める

simutrans本体は、配ってよいものを書いた許可リスト（`engine-files.default.json`）に載っているものだけを配ります。リストに載っていないフォルダやファイルは配らず、公開のたびに「配らないもの」として表示します。

リストに書いても配らないもの（絶対に配らないもの）も決めています。

| 種類 | 対象 |
|---|---|
| フォルダ | `save`、`screenshot`、`addons` |
| セーブデータとパスワード | `*.sve`、`*.sv_`、`*pwdhash*`、`settings.xml` |
| 実行できるもの | `*.bat`、`*.cmd`、`*.ps1`、`*.vbs`、`*.js`などのスクリプト、選んだ本体以外の`*.exe`、`*.msi`など |
| そのほか | ログ（`*.log`）、ショートカット（`*.lnk`、`*.url`）、レジストリ（`*.reg`） |

paksetのフォルダ（`.pak`が入っていて、許可リストに書いていないフォルダ）は、本体には入れません。paksetはpaksetの公開で別に配り、友人のPCでは本体のフォルダの中に置かれます。

`themes`のように中身が混ざりやすいフォルダは、`themes/*.tab`のように名前を決めて、直下のファイルだけを配ります。Windowsが自動で作るファイル（`desktop.ini`、`Thumbs.db`）と、隠しファイルやシステムファイルも配りません。

paksetの公開でも、実行ファイルなど（`.exe`、`.dll`、`.bat`、`.ps1`など）は警告を出して配りません。simutransのスクリプト（`.nut`）は、paksetの正式な中身なので配ります。

### サーバーリストに署名する

配信フォルダが書き換えられても友人のPCを守れるように、サーバーリスト（`list-ランダムな文字.json`）に署名しています。署名の方式はECDSA P-256とSHA-256で、`manifest.json`のバイト列そのものに署名し、`manifest.sig.json`として隣に置きます。公開のスクリプトが、サーバーリストを書き換えるたびに署名し直します。

サーバーリストには、paksetと本体のファイル一覧（`index.json`）のSHA256が書いてあります。ファイル一覧には、各ファイルのSHA256が書いてあります。そのため、サーバーリストの署名を確かめれば、ファイル一覧とすべてのファイルが、管理者が公開したとおりかを確かめられます。

署名の鍵（秘密鍵）は`%LOCALAPPDATA%\InfraLauncherServer\signing-key.dat`に置き、Windowsの機能（DPAPI）で、鍵を作ったWindowsユーザーでしか開けないように暗号化しています。ファイルをコピーされても、ほかのPCやほかのユーザーでは使えません。

鍵のバックアップ（`signing-key-backup.json`）は、パスワードから鍵を作って暗号化しています。パスワードからの鍵の作成にPBKDF2-SHA256を30万回、暗号化にAES-256-CBCを使い、HMAC-SHA256で改ざんを検出します。パスワードは8文字以上です。

### 確認コードで鍵を見分ける

友人は、最初に管理者から聞いた確認コードをランチャーに入力します。確認コードは、公開鍵のSHA256の先頭80ビットを、16進数で20文字にしたものです。ランチャーは確認コードを画面に表示しないので、友人は管理者から聞かない限り登録できません。これで、偽のサーバーリストを教えられても、確認コードが合わず、登録できません。

確認コードは秘密ではありません。ただし、配信サーバーの中に置いて伝えると、配信フォルダを書き換えた人が確認コードも差し替えられるので、DiscordのDMなど別の経路で伝えます。

### HTTPSで通信を守る

HTTPSにすると、通信が暗号化され、途中で中身を見られたり差し替えられたりしなくなります。書き換えは署名でも防げますが、HTTPSは、古い署名付きのサーバーリストを送りつけられることも防ぎます。

証明書はLet's Encryptの無料の証明書で、win-acmeで取得と更新をします。win-acmeはGitHubの公式の配布元からHTTPSで取得し、GitHubがSHA256を公開していれば照合してから使います。win-acmeの電子署名は自己署名のため、署名の状態は参考として表示するだけにしています。

## ランチャー側の確かめ方

ランチャーは、サーバー側の仕組みを前提に、次のことを確かめます。

サーバーリストは、登録した確認コードの鍵で正しく署名されているときだけ読み込みます。署名がない、中身と合わない、鍵が変わった、のいずれかなら読み込みを止めます。鍵が変わったときも、新しい確認コードは画面に出しません。simutrans本体を入れるのは、確認コードを登録したサーバーリストからだけです。

ファイル一覧は、`..`を含むパスや絶対パス、Windowsで作れない名前を受け付けません。paksetの一覧に実行ファイルが入っていれば受け付けず、本体の一覧でも、許すのはサーバーリストに書かれた本体のexeと、直下の`.dll`だけです。Web上のサーバーリストから、手元のファイル（`file://`）を指すことも受け付けません。

ダウンロードしたファイルは、一時フォルダでSHA256を確かめてから置きます。ランチャーが入れた本体を初めて起動するときは、配布元と場所とSHA256を表示して、友人に承認してもらいます。承認はSHA256で覚え、本体が変わればまた確認します。起動の直前にもSHA256を計算し直し、インストールしたあとに書き換えられていれば起動しません。起動のときは`-noaddons`を付け、友人のPCにある別のアドオンを読み込まないようにしています。

## 防げないこと

次のことは、この仕組みでは防げません。運用で気をつけてください。

VPSに管理者としてログインされると、署名の鍵も使えるので、正しい署名の付いた偽のファイルを配られてしまいます。リモートデスクトップには強いパスワードを使い、可能ならVPSの管理画面で接続元のIPアドレスを絞ってください。Windows Updateも欠かさず当ててください。

友人が、偽の確認コードを教えられて登録してしまうと防げません。確認コードは管理者本人から、いつもと同じ経路で受け取るよう伝えてください。

HTTPSにしていない場合は、通信の中身は暗号化されず、古い署名付きのサーバーリストを送りつけられるおそれがあります。古いサーバーリストに書かれているのも管理者が以前公開したファイルなので、知らない実行ファイルが入ることはありません。

大量の要求でサーバーを止める攻撃（DoS）は防げません。simutransのネットワークゲームそのものの安全性（接続してきたプレイヤーの操作など）も、この仕組みの対象外です。

## 運用のまとめ

| やること | 理由 |
|---|---|
| リモートデスクトップのパスワードを強くする | VPSに入られると署名の鍵も使われるため |
| 鍵のバックアップをVPSの外に保管する | VPSを作り直しても同じ確認コードを使い続けるため |
| 公開はいつも同じWindowsユーザーで行う | 鍵はそのユーザーでしか開けないため |
| 確認コードは配信サーバー以外の経路で伝える | 配信フォルダと一緒に差し替えられないようにするため |
| HTTPSにする | 通信の暗号化と、古いサーバーリストの送りつけを防ぐため |
| 鍵が盗まれたおそれがあれば作り直す | 盗まれた鍵で署名されたものを、友人のランチャーが受け付けないようにするため |
